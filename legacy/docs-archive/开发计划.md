# 3. M1 客户端本地核心（P0）

> 对应设计文档 §75 P0 + §31 本地事务 + §32.1 Version Guard

## 3.1 任务清单

| # | 任务 | 模块 | 设计依据 |
|---|---|---|---|

| 2 | Migration 框架（schema_version + 顺序执行 + 失败恢复） | `db/migration.rs` | §32 |
| 3 | 实体 Repository（notes/branches/attributes/blobs CRUD） | `db/repositories/` | §7-10 |
| 4 | 本地事务封装（Entity + FTS + Change + Outbox 同事务） | `db/transaction.rs` | §18, §64 |
| 5 | Change Log（UUIDv7/ULID、快照 payload 序列化） | `sync/change.rs` | §11, §16 |
| 6 | Sync Outbox（PENDING/SENDING 状态机、崩溃恢复） | `sync/outbox.rs` | §7, §27 |
| 7 | Sync Cursor（pull 批次事务 + 推进规则） | `sync/cursor.rs` | §31, §52 |
| 8 | FTS5 表 + 事务内维护 + 重建工具 | `search/fts.rs` | §45-47 |

## 3.2 验收标准

```bash
cd lightnote-client/src-tauri && cargo test
```

必须覆盖（对应 §47 测试矩阵的本地部分）：

- 创建/修改/删除笔记 → entity_changes + sync_outbox 同事务写入
- 回滚场景：变更失败时 Change/Outbox 不残留
- Outbox 状态机：PENDING→SENDING→REMOVE，崩溃后 SENDING 超时恢复为 PENDING
- Pull 应用：应用 Change 不写 Outbox（防环路）；local.version > change.version 时跳过应用但推进 cursor
- 批量 pull 中途崩溃 → 事务回滚 → 重放不丢不重
- FTS 与实体同步更新，重建命令可用

> 对应 §22/§22.1/§23/§25/§26 + §49-51 + §9.1/§9.2

## 4.1 任务清单

| # | 任务 | 模块 | 设计依据 |

| 6 | Pull API：`WHERE server_sequence > ? ORDER BY LIMIT` + hasMore 翻页 | `sync/pull.go` | §51 |
| 7 | Notes/Branches/Attributes REST API（业务端点） | `api/` | §28 |
| 8 | 设备管理 API（列表/撤销） | `api/devices.go` | §9, §9.1 |

## 4.2 验收标准

```bash
cd lightnote-server && go test ./... && go vet ./...
```

必须覆盖：

- Push 幂等：重复 changeId → ALREADY_APPLIED 且不重复改实体
- 冲突：base_version != current → 生成冲突副本 + 新 change 写入
- 序列：AUTOINCREMENT 严格单调；回滚后不重复；并发 push（多 goroutine）序列唯一
- Pull：gap 容忍、hasMore 分页正确、cursor 只推进不跳跃
- JWT：伪造 device_id 被拒（以 JWT 为准）；吊销设备后 token 失效
- 与 M1 联调：Rust 测试实例 push → Go server → 另一个 Rust 实例 pull 一致

# 5. M3 Blob / FTS / 设备（P2）

> 对应 §40-44.1 + §45-47

## 5.1 任务清单

| # | 任务 | 模块 | 设计依据 |
|---|---|---|---|
| 1 | 服务端 Blob：内容寻址存储（hash 分层目录）、init/chunks/complete、SHA-256 校验 | `api/blobs.go` | §40-44 |
| 2 | 客户端 Blob Manager：上传分片、断点续传、重复 chunk 容忍 | `blob/manager.rs` | §42-43 |
| 3 | 客户端 Blob Lazy Download：队列 + 优先级 + 临时文件原子 rename | `blob/download_queue.rs` | §44.1 |
| 4 | 服务端 Blob 下载端点 + 缺失处理 | `api/blobs.go` | §44.1 |
| 5 | 设备管理 UI 数据源 + 服务端设备状态展示 | 联调 | §9 |

## 5.2 验收标准

- 上传中断重试：chunk 已存在可跳过，最终 hash 校验通过
- 上传损坏数据 → REJECT，本地重试
- 拉取到含 blobId 的 change 时实体先应用，blob 后台到达；打开笔记时缺失 blob 立即优先下载
- 下载校验失败 → 重试 → FAILED 标记且不阻塞 UI
- 内容去重：两个笔记引用同一 blob，服务端只存一份

# 8. 风险与注意事项

| 风险 | 对策 |
|---|---|
| Rust/Go 工具链未装 | M0 第一步安装，完成后验证版本 |
| rusqlite FTS5 需要 bundled 特性 | Cargo.toml 显式 `rusqlite = { features = ["bundled"] }`（bundled 自带 FTS5） |
| SQLite 并发：Go server 多连接写 | 单写者连接池（默认 1 写连接）+ busy_timeout；AUTOINCREMENT 保证序列 |
| modernc.org/sqlite 性能 | 个人量级无虞；必要时换 CGO 驱动（部署加 libsqlite3 依赖） |
| Tauri GUI 在 WSL 开发体验 | 核心逻辑与 UI 解耦，先在 Rust CLI 层验证 |
| 同步环路回归 | M1 单元测试锁定"Pull 不写 Outbox" + M5 双客户端长跑 |
| server_sequence 回滚复用 | M2 集成测试覆盖回滚后序列不复用（§22.1） |
